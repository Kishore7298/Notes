## 🔍 What is an API?

**API (Application Programming Interface)** allows software components to communicate using defined rules and protocols.

**Example (Ticketmaster-like app):**

* **Client → Server:** `GET /events`
* **Server → Database:** Query events
* **Database → Server → Client:** Return event data

---

## ⚙️ API Protocols Overview

| Context             | Recommended Protocol     | Description                                          |
| ------------------- | ------------------------ | ---------------------------------------------------- |
| **Client ↔ Server** | **REST** (default)       | Built on HTTP (`GET`, `POST`, etc.)                  |
|                     | GraphQL                  | Flexible; clients request only needed data           |
| **Server ↔ Server** | RPC                      | Efficient for internal microservice communication    |
| **Real-time**       | WebSocket / SSE / WebRTC | Persistent connections for streaming or live updates |

> ✅ **Rule of thumb:** If unsure — choose **REST** (95% correct in interviews).

## 🌐 REST API Design

### 🔹 Core Concept

REST revolves around **resources** → typically your **core entities** (nouns).

Example entities for Ticketmaster:

```
events, venues, tickets, bookings
```

### 🔹 URL & Resources

Resources are represented in **plural noun form** within URLs.

| Operation | Example Endpoint      | Meaning          |
| --------- | --------------------- | ---------------- |
| List      | `GET /events`         | Get all events   |
| Retrieve  | `GET /events/{id}`    | Get one event    |
| Create    | `POST /events`        | Create new event |
| Update    | `PATCH /events/{id}`  | Partial update   |
| Delete    | `DELETE /events/{id}` | Remove event     |

> ❗ Don’t use verbs in URLs (`/createEvent`).
> The **HTTP method** expresses the action.

---

## 🧩 HTTP Methods

| Method     | Purpose          | Idempotent? | Example               |
| ---------- | ---------------- | ----------- | --------------------- |
| **GET**    | Retrieve data    | ✅ Yes       | `GET /events`         |
| **POST**   | Create new data  | ❌ No        | `POST /events`        |
| **PUT**    | Replace resource | ✅ Yes       | `PUT /events/{id}`    |
| **PATCH**  | Partial update   | ✅ Yes       | `PATCH /events/{id}`  |
| **DELETE** | Remove resource  | ✅ Yes       | `DELETE /events/{id}` |

> Don’t overthink PUT vs PATCH vs POST — focus on clarity.

---

## 🧾 Input Types in REST

| Type                | Used For                       | Example                                 |
| ------------------- | ------------------------------ | --------------------------------------- |
| **Path Parameter**  | Identifies a specific resource | `/events/123`                           |
| **Query Parameter** | Optional filters               | `/events?city=LA&date=2025-01-01`       |
| **Request Body**    | Data payload for create/update | `{ "title": "Concert", "date": "..." }` |

**Rules of thumb:**

* Required identifier → Path param
* Optional filter → Query param
* Sending data → Request body

---

## 📦 Responses

* **Status Code**

  * `2xx` → Success (`200 OK`, `201 Created`)
  * `4xx` → Client Error (`400 Bad Request`, `401 Unauthorized`, `404 Not Found`)
  * `5xx` → Server Error (`500 Internal Error`)
* **Response Body**

  * Usually in JSON format
  * Don’t list every field — use shorthand:

    ```
    GET /events → returns List<Event>
    ```

## 🧠 GraphQL Overview

### 🔹 Background

* Created by **Facebook (2012)** to fix REST inefficiencies on slow mobile networks.
* Open-sourced in **2015**.
* Lets clients **specify exactly the fields they need** in a single query.

### 🔹 Example

```graphql
query {
  event(id: "123") {
    name
    date
    venue { name address }
    tickets { section price available }
  }
}
```

✅ **One request**, all needed data.

🆚 **REST Equivalent:**
Multiple calls – `/events/123`, `/venues/{id}`, `/tickets/{id}`

---

## ⚠️ GraphQL Gotchas

* **N + 1 Problem:** Multiple nested queries cause excessive DB calls.

  * Solved via **batching** or **DataLoader** pattern.
* **Complexity:** Harder caching, authorization, and performance tracing.
* **Usage:** Ideal for client-driven flexibility (e.g. mobile apps).

## 🧩 Summary: When to Use What

| Scenario                                           | Recommended API Type          |
| -------------------------------------------------- | ----------------------------- |
| General web service                                | **REST**                      |
| Complex data relationships, client-specific fields | **GraphQL**                   |
| Internal microservice communication                | **RPC (gRPC)**                |
| Real-time chat / updates                           | **WebSockets / SSE / WebRTC** |

---

## 🧭 Interview Tips

* Don’t spend >5 minutes on API design.
* Use **plural nouns**, clean resource mapping.
* Mention **REST by default**.
* Highlight **GraphQL** only if relevant.
* Keep input/output format **concise and consistent**.
* Focus on **clarity**, not perfection.
