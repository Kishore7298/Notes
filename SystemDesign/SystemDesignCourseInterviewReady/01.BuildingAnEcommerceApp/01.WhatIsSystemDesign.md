# System Design — Introduction

## 1. What is System Design?

System design = deciding:

* **What components** are needed
* **Where** they are placed
* **How they interact**
* How they satisfy **business requirements** 

---

## 2. How to Evaluate a Design

Three important criteria:

| Criteria               | Question                          |
| ---------------------- | --------------------------------- |
| **Simplicity**         | Is it easy to understand/change?  |
| **Fidelity**           | Does it satisfy the requirements? |
| **Cost effectiveness** | Is it affordable and feasible?    |



---

## 3. Start With the Business Problem

Example: A friend sells T-shirts offline/social media and wants to sell online.

**Don't immediately build an e-commerce platform.**

First ask:

> **Does an existing solution solve the problem?**

If yes → **use it.**

---

## 4. Amazon vs Shopify

### Amazon

Doesn't fully satisfy the requirements because the business wants:

* More control over **store look & feel**
* More control over **recommendations**



### Shopify

Better fit because it provides:

* Own webpage/storefront
* More customization
* Payment integrations
* Delivery integrations



### Key principle

> **An architect's job is to solve the business problem, not to build a technical solution unnecessarily.**

If an existing solution works → **use it.** 

---

# 5. When System Design Becomes Necessary

Business grows to ~100 sales/day and Shopify now has limitations.

### Problem 1: Delivery tracking

Customers ask:

> "Where is my order?"

Support has to manually check the delivery portal and respond.

### Problem 2: International payments

International customers can't pay because the existing payment gateway doesn't support their cards/currency.

This potentially causes **10–20% lost sales**. 

---

## 6. Don't Replace Shopify — Extend It

First check whether Shopify/its partners can fix the problems.

They can't.

So instead of rebuilding the entire e-commerce system:

> **Build a custom wrapper around Shopify.**



```text
                 Shopify
                    │
          ┌─────────┴─────────┐
          │                   │
   Custom Payment       Custom Tracking
       Page                  Page
          │                   │
   Payment Providers    Delivery Provider
```

**Idea:** Keep what already works; build only what is missing.

---

# 7. External Systems = Black Boxes

You don't need to know how Shopify/payment/delivery systems work internally.

You only need to know:

* How to interact with them
* What input they expect
* What output they provide

```text
Your System ─── API ───► External System
                           (Black Box)
```



---

# 8. APIs

The custom payment/tracking pages need to communicate with our server.

**API = interface/contract between client and server.**

```text
Client
  │
  │ Request
  ▼
 Server/API
  │
  │ Response
  ▼
Client
```

An API defines:

* What request to send
* What response to expect



### Mental model

> **API ≈ a function exposed over a network**

```text
Input → Function → Output
```

The API can be implemented in **Go, Python, Java, etc.** The client only cares about the contract. 

---

# 9. Basic Server Model

```text
Client
   │
   ▼
API Request
   │
   ▼
Server
   │
   ▼
Business Logic
   │
   ▼
Response
```

Code can be deployed to a cloud server and executed to handle incoming requests. Modern CI/CD tools can automate deployment. 

---

# ⭐ Remember This

```text
Business Problem
      ↓
Existing Solution?
      ↓
   YES → Use it
      ↓
New requirements appear
      ↓
Identify gaps
      ↓
Keep existing system
      +
Build only missing pieces
      ↓
Design APIs & interactions
```

### Core principles

* **Solve the business problem, not the technical problem.**
* **Don't build what already exists.**
* **Use existing systems wherever possible.**
* **Extend/replace only the parts that don't satisfy requirements.**
* **Evaluate designs on simplicity, fidelity and cost.**
